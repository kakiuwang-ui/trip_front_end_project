    核心流程

    三条主链路，落到代码

    以下步骤与代码片段直接来自 app/api 下的实现，非示意。

    ① 事务性预订 · 防超卖

    prisma.$transaction 内先批量查询、补齐逐日库存，再用条件更新原子扣减。查询从 N×3 降至 N+3，并发下靠 booked < quota 条件杜绝超卖。

    1

    生成日期数组

    由 checkIn 到 checkOut 逐日展开为 dateArray，先校验退房晚于入住、入住不早于今天。

    2

    批量查询 + 补齐库存

    一次 findMany({ date: { in } }) 拉全区间；缺失日期用 createMany 以房型 stock 为 quota 补齐。

    3

    内存逐日校验并算价

    检查 isClosed 与 booked >= quota 售罄，累加每日 price（日价可覆盖基础价）。

    4

    条件更新原子扣减

    updateMany 带 booked < quota 条件；count === 0 即判定并发冲突并整体回滚。

    取舍 · Trade-off

    为什么条件更新而非先读后写：先读后写在并发下有 TOCTOU 竞态；把「检查+扣减」压成一条 updateMany(booked < quota)，用受影响行数判定成败，天然串行化到那一行。N+3 而非 N×3：批量查询 + createMany 补齐，省去逐日多次往返。

    app/api/bookings/route.tsx
    // 逐日原子更新：并发安全，查询 N+3
for (const date of dateArray) {
  const updated = await tx.roomAvailability.updateMany({
    where: {
      roomTypeId,
      date,
      booked: { lt: quota }   // ← 关键条件
    },
    data: { booked: { increment: 1 } }
  });

  if (updated.count === 0) {
    throw new Error(`已售罄（并发冲突）`);
  }
}
    并发预订 · 最后 1 间房
    quota 1 · booked 0
    UPDATE room_availability SET booked = booked + 1 WHERE booked < quota  →  受影响行数决定成败，只有 1 个请求能改到那一行

    ② AI 两阶段推荐 · 流式

    先用 temperature=0 做确定性意图提取，转成 Prisma 查询取真实库存，再用 temperature=0.7 流式生成文案，经 SSE 回包。

    1

    限流与入参校验

    超频返回 429；取最近 3 条对话 slice(-3) 作为提取上下文。

    2

    结构化意图提取

    withStructuredOutput(searchSchema)（Zod）提取目的地/价格/星级等条件，未提及则置 null。

    3

    构建 Prisma 查询

    以 status: 'published' 为基，按提取条件拼 where.OR，查真实酒店与价格。

    4

    流式文案生成

    第二个模型 streaming: true，逐 chunk 写入 ReadableStream 返回。

    为什么两段温度：提取阶段 t=0 求确定，保证结构化 JSON 稳定可解析；生成阶段 t=0.7 求自然。为什么先查库再生成：让模型基于真实库存推荐，杜绝「幻觉」出不存在的酒店。

    ③ 请求鉴权 · verifyAuth

    每个受保护接口首行调用 verifyAuth()：验签 JWT，再查 Redis 黑名单确认未登出，解出 { userId, role, roleId, merchantId } 供细粒度权限判断。

    1

    取 Bearer Token

    无 Authorization: Bearer 头直接 401。

    2

    验签 + 黑名单

    jwt.verify 通过后再查 isTokenBlacklisted(token)，已撤销则 401。

    3

    解析有效商户

    getEffectiveMerchantId：MERCHANT 返回自身 id，STAFF 返回其所属 merchantId。

    4

    细粒度权限

    审核/删除额外校验 HOTEL_AUDIT / HOTEL_DELETE 权限名。

    取舍 · Trade-off

    为什么双层鉴权：JWT 无状态、免每请求查库；但登出/改角色需即时失效 → 用 Redis 黑名单 + 权限缓存兜底。STAFF 复用 merchantId：继承所属商户的数据边界，无需为职员另建一套权限体系。

    app/api/utils/auth.ts
    const decoded = jwt.verify(token, JWT_SECRET);

// 检查 token 是否已被登出撤销
if (await isTokenBlacklisted(token)) {
  return { success: false,
    error: 'Token 已被撤销', status: 401 };
}

return { success: true, user: decoded };

    实现细节

    八段真实工程实现

    从鉴权刷新、限流、缓存到事务、错误处理与查询优化，均取自源码，非示意。

    ① 无感刷新 · failedQueue
    Access Token 过期时，isRefreshing 锁保证只发一次刷新请求，并发的 401 请求进入 failedQueue 排队；刷新成功后 processQueue 用新 token 逐一重放，排除 login/refresh 自身以防死循环。
    app/lib/request.ts
    if (isRefreshing) {
  // 刷新进行中：排队，拿到新 token 再重发
  return new Promise((resolve, reject) => {
    failedQueue.push({ resolve, reject });
  }).then((token) => {
    originalRequest.headers['Authorization'] = 'Bearer ' + token;
    return request(originalRequest);
  });
}
isRefreshing = true;
    ② 权限缓存 · Redis
    checkPermission 先查 perm:{userId}（TTL 900s = 15 分钟），未命中才走 role → rolePermission → permission.name 的窄字段查询并回填；空权限集也缓存，避免高频用户反复击穿数据库。
    app/api/utils/permissions.ts
    const PERM_TTL = 900; // 15 分钟

const cached = await redis.smembers(`perm:${userId}`);
if (cached.length) return new Set(cached);

// 未命中 → 窄查询后回填（空集也缓存防击穿）
await redis.sadd(`perm:${userId}`, ...perms);
await redis.expire(`perm:${userId}`, PERM_TTL);
    ③ 审计日志 · 原子事务
    酒店状态变更与留痕写在同一 $transaction 内：tx.hotel.update 改状态、tx.hotelAuditLog.create 记录 operatorId / oldStatus / newStatus / comment，二者要么全成功要么全回滚，审计不漏不重。

    ⑤ 接口限流 · Redis 固定窗口
    checkRateLimit 用 redis.incr 计数，首次访问设 expire；超限用剩余 ttl 算 retryAfterSec。AI 推荐限 10 次 / 小时 / 用户，超限返回 429。Redis 故障时降级放行，不误伤正常请求。
    app/lib/rate-limit.ts
    const count = await redis.incr(`ratelimit:${key}`);
if (count === 1) await redis.expire(redisKey, windowSec);

if (count > limit) {
  const ttl = await redis.ttl(redisKey);
  return { allowed: false, retryAfterSec: ttl };
}
return { allowed: true, retryAfterSec: 0 };

    可靠性 · Redis 故障不阻断主流程

    Redis 承担限流、Token 黑名单与权限缓存，但均以「失败降级」接入——外部依赖抖动时业务照常，不因缓存层拖垮主链路：

    • 限流 异常时 allowed: true 放行
    • 黑名单 查询异常时 return false 放行；写入用 EX = 剩余有效期 到期自清理
    • 权限缓存 读写失败即跳过缓存、回落数据库查询
    • 连接 ioredis lazyConnect + maxRetriesPerRequest: 3，globalThis 单例复用
    安全设计

    纵深防御，逐层收口

    从密码存储到接口鉴权、限流与注入防护，安全措施贯穿每一层，均可在代码中验证。

    密码与令牌

    密码 bcryptjs 哈希（salt rounds=10），明文不落库；JWT 双 Token（Access 1h / Refresh 7d）。

    登出即失效

    登出把 Token 写入 Redis 黑名单，EX = 剩余有效期到期自清；verifyAuth 每次校验黑名单。

    接口限流

    登录与 AI 推荐均接 Redis 固定窗口限流（AI 10次/小时），防暴力破解与滥用，超限 429。

    RBAC 双层

    四角色 + 细粒度 Permission；审核/删除额外校验 HOTEL_AUDIT / HOTEL_DELETE，权限走 Redis 缓存。

    输入校验

    Zod 运行时 Schema 校验请求体，与 LangChain 结构化输出复用同一套定义，非法入参早失败。

    注入与上传

    Prisma 参数化查询免疫 SQL 注入；上传文件名正则净化防路径穿越；JWT_SECRET 启动即校验强制配置。

    创新点

    七项工程决策

    每一项都落到具体代码，可在仓库中逐一验证。

    01 · 并发安全

    事务性防超卖

    $transaction 内对每个入住日逐日 upsert 库存，booked >= quota 即整体回滚，由 InnoDB 行锁保护原子递增，从存储层杜绝超卖。

    02 · AI

    LLM 两阶段推荐

    意图提取 temperature=0 走结构化输出，文案生成 temperature=0.7，结合实时库存以 SSE 流式推荐。

    03 · 安全

    RBAC 双层鉴权

    四角色（USER / STAFF / MERCHANT / ADMIN）+ 细粒度 Permission；JWT 双 Token（1h / 7d），登出经 Redis 黑名单失效，状态变更原子写审计日志。

    04 · 架构

    多端统一

    Web 后台与小程序复用同一套 Next.js API Routes；Taro 一套 React 代码编译微信 / 支付宝 / 抖音 / H5 等 8+ 平台。

    05 · 类型

    全栈类型安全

    Prisma 生成数据库类型，前后端共享 types/index.ts；LangChain 结构化输出与 Zod 校验复用同一套 Schema。

    06 · 性能

    长列表渲染优化

    服务端分页（10 条 / 页）+ 客户端无限滚动追加，loadingMore 互斥锁 + hasMore 状态，首屏渲染线性可控。

    07 · 工程化

    规范与自动化

    JSDoc 注释经 next-swagger-doc 自动生成 OpenAPI 文档；文件上传名安全化；Prisma 单例防热更新连接泄漏。

    权限矩阵

    四角色 · 基于角色的访问控制

    角色在 JWT Payload 中携带，API 层由 verifyAuth() 解码后按需二次查询 Permission 表。
